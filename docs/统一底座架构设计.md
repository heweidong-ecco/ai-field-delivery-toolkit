### 1.2 核心原则

| 原则       | 说明                                                 |
| ---------- | ---------------------------------------------------- |
| 模块独立   | 每个模块是独立目录，可单独导入、单独测试、单独启用   |
| 底座共享   | 所有模块通过统一底座读取配置、记录日志、调用安全基座 |
| 安全内建   | 安全基座在底座层，所有模块的输入输出自动经过安全过滤 |
| 降级统一   | 所有 AI 调用必须通过降级管理器执行，不允许绕过       |
| 配置驱动   | 模块行为由配置决定，不硬编码                         |
| 无外部依赖 | 核心功能离线可用，外部 API 是可选增强                |

## 三、模块间 API 契约（文档型）

### 3.1 统一响应格式（设计契约，HTTP 层不套包装）

> ⚠️ **实际 API 返回原始 JSON + HTTP 状态码，未套 `{code,message,data}` 包装**。以下为设计期契约。

目标标准响应（设计期）：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

| 字段      | 类型              | 说明                      |
| --------- | ----------------- | ------------------------- |
| `code`    | int               | 0 为成功，非 0 为业务错误 |
| `message` | string            | 状态描述                  |
| `data`    | object/array/null | 实际数据                  |

### 3.2 统一错误码（设计契约）+ 实际 HTTP 状态码

**实际 HTTP 层使用的状态码**：

| HTTP 状态码 | 含义 |
| ------ | ------ |
| 400 | 需人工确认 / 参数错误（如诊断未定稿确认禁止裁剪、文档包未确认） |
| 403 | 质量门禁未过（如数据未达标不进原型，未勾选强制继续） |
| 404 | 资源不存在（run_id / case_id / 项目不存在） |
| 429 | 预算超限（诊断/映射 LLM 调用超预算） |

设计期业务错误码：

| 错误码 | 含义               |
| ------ | ------------------ |
| 0      | 成功               |
| 1001   | 参数错误           |
| 1002   | 认证失败           |
| 1003   | 权限不足           |
| 1004   | 资源不存在         |
| 2001   | 数据接入失败       |
| 2002   | 数据质量不合格     |
| 2003   | 数据清洗失败       |
| 3001   | 模型调用失败       |
| 3002   | 模型超时           |
| 3003   | 结构化输出验证失败 |
| 3004   | 流式输出中断       |
| 4001   | Docker 构建失败    |
| 4002   | 部署失败           |
| 5001   | 监控数据上报失败   |
| 6001   | 反馈回流失败       |
| 7001   | 裁剪引擎约束不完整 |

## 四、五步裁剪引擎详细设计

### 4.1 约束输入模型

```yaml
customer_constraints:
  budget: 200000              # 预算（元）
  hardware:
    cpu: "8核"
    memory_gb: 32
    gpu: null                 # 无 GPU
    storage_gb: 500
  environment:
    os: "ubuntu-22.04"
    docker: true              # 是否支持 Docker
    network: "intranet-isolated"  # 内网隔离
    external_access: false    # 是否可访问外网
  data:
    total_records: 300000     # 总数据量
    daily_new: 500            # 每日新增
    format: ["csv", "json"]
    quality: "dirty"          # clean/medium/dirty
  users:
    total_users: 100
    concurrent_peak: 20
  compliance:
    data_residency: "on-premise"
    pii_sensitive: true
  timeline_weeks: 2
```

### 4.2 五步执行规则

| 步骤                    | 执行逻辑                                                     | 输出       |
| ----------------------- | ------------------------------------------------------------ | ---------- |
| **1. 质疑每一项需求**   | 逐项检查约束，标记哪些需求真实必须、哪些是假设               | 必要性评估 |
| **2. 删除所有能删除的** | 将 MVP 模块中的功能与约束比对，标记可删除的模块和功能        | 删除清单   |
| **3. 简化与优化**       | 对保留模块给出简化配置（如单模型直连替代网关、裸机替代 K8s） | 简化配置   |
| **4. 加速周转时间**     | 基于时间窗口和约束，给出任务并行和优先级建议                 | 排期建议   |
| **5. 自动化**           | 仅建议客户有持续能力的自动化项                               | 自动化建议 |

### 4.3 裁剪方案输出格式

```json
{
  "customer_id": "xxx",
  "plan_version": "1.0.0",
  "enabled_modules": ["data_prep", "prototype_assembler", "deploy_hardener", "diagnosis"],
  "deleted_modules": ["monitor", "data_flywheel"],
  "simplifications": {
    "deploy_hardener": {"mode": "bare-metal"},
    "prototype_assembler": {"agent_loop": "react-only"}
  },
  "automations": [],
  "timeline_suggestion": {
    "data_prep": "3 days",
    "prototype": "2 days",
    "deploy": "2 days"
  }
}
```


## 五、统一底座详细设计

### 5.1 配置中心

| 设计项         | 规则                                                               |
| -------------- | ------------------------------------------------------------------ |
| 配置来源优先级 | 环境变量 > 本地 `config.yaml` > 默认值                             |
| 统一入口       | 所有模块通过 `core.config.get_settings()` 读取，禁止直接读环境变量 |
| 模块注册       | 模块在启动时向底座注册，声明依赖和配置项                           |
| 敏感配置       | API Key、密码必须通过环境变量传递，禁止写入配置文件                |
| 变更记录       | 配置变更必须记录到日志                                             |

### 5.2 安全基座

| 组件     | 设计规则                                                                         |
| -------- | -------------------------------------------------------------------------------- |
| PII 检测 | 提供统一的 `detect_pii(text)` 和 `mask_pii(text)` 接口，所有模块输入输出自动经过 |
| 注入拦截 | 提供 `is_injection(text)` 接口，命中拦截模式返回 `True`，由调用方决定后续动作    |
| 输出审核 | 提供 `review_output(text)` 接口，返回 `{passed, reason, masked_text}`            |
| 强制原则 | 安全基座在底座层默认开启，不允许模块单独关闭                                     |

### 5.3 日志系统

| 设计项   | 规则                                          |
| -------- | --------------------------------------------- |
| 日志库   | loguru                                        |
| 输出目标 | 控制台 + 按天滚动的文件                       |
| 格式     | `时间                                         | 级别 | 模块名 | 消息` |
| 脱敏     | 日志消息必须经过安全基座的 PII 脱敏后才能输出 |
| 禁止记录 | API Key、密码、完整用户 PII                   |

### 5.4 版本管理

| 版本类型   | 规则                                   |
| ---------- | -------------------------------------- |
| 代码版本   | 语义化版本，`core.__version__` 记录    |
| 提示词版本 | 提示词文件独立于代码，使用版本号命名   |
| 模板版本   | 场景模板有版本号，生产使用必须固定版本 |
| 回滚       | 切换版本号即可，不覆盖历史版本         |

### 5.5 降级管理

| 设计项   | 规则                                                 |
| -------- | ---------------------------------------------------- |
| 降级路径 | 正常调用 → 缓存 → 规则 → 人工 → 拒绝                 |
| 统一入口 | `DegradationManager.execute()`，所有 AI 调用必须经过 |
| 降级记录 | 每次降级触发必须记录：时间、原因、降级到的层级       |
| 恢复     | 主路径恢复后自动切回，无需人工                       |


## 六、数据库设计

### 6.1 表结构

| 表名             | 字段                                                              | 用途         |
| ---------------- | ----------------------------------------------------------------- | ------------ |
| `projects`       | id, name, customer_id, status, created_at, updated_at             | 项目记录     |
| `data_versions`  | id, project_id, version, source, record_count, created_at         | 数据版本     |
| `eval_sets`      | id, project_id, version, sample_count, coverage, created_at       | 评测集       |
| `prototype_runs` | id, project_id, template_name, status, created_at                 | 原型运行记录 |
| `deployments`    | id, project_id, mode, status, created_at                          | 部署记录     |
| `feedbacks`      | id, project_id, request_id, type, content, created_at             | 反馈记录     |
| `crop_plans`     | id, customer_id, constraints_json, plan_json, version, created_at | 裁剪方案     |
| `assets`         | id, project_id, type, name, path, created_at                      | 可复用资产   |

### 6.2 设计原则

| 原则                  | 说明                                   |
| --------------------- | -------------------------------------- |
| 所有表含 `id` 主键    | 无复合主键                             |
| 所有表含 `created_at` | 时间戳自动记录                         |
| 多租户字段后置        | MVP 暂不加 `tenant_id`，但预留扩展能力 |
| 软删除                | 数据不做物理删除，用 `status` 标记     |
