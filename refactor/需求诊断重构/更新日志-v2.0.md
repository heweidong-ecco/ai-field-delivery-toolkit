# 需求诊断模块 · 更新日志 v2.0

> 日期：2026-08-29
> 版本号：v2.0（需求诊断输出深度重构）
> 关联方案：[重构方案-v1.0.md](./重构方案-v1.0.md)（一期/二期已落地）、[决策过程-v2.md](./决策过程-v2.md)
> 本轮主题：把诊断报告从「一页打分表」重构为「多轮累积的详细需求文档」，并让完整对抗评审过程全程留痕可见。

## 1. 变更内容（对应任务书 1-5）

### 1.1 三 Agent 输出无长度限制、完整思考（`diagnosis/agents.py`）

- 删除 Generator / Critic / Reviewer prompt 里所有长度限制：「150字内」「草稿要点」「不超过 3 个澄清问题」等全部移除。
- **Generator 新 schema**：`requirement_understanding`（背景/痛点/目标/约束，详细）、`dimension_analysis`
  （每维 `{score, analysis 完整论证, evidence 引用需求原文, implications 对客户影响}`）、`scope`（做什么/不做什么）、
  `functional_requirements`（可验收条目）、`non_functional_requirements`（每条含 title/detail/standard）、
  `data_requirements`（数据来源/数据量/质量/安全合规/资源）、`risks`（每条含 likelihood/impact/mitigation）、
  `assumptions`、`clarification_questions`（每条带 why 为什么问）、`implementation_phases`（分阶段建议）、
  `draft_sections`（背景/目标/范围/功能需求/非功能需求/验收标准，详细章节草稿）。
- **Critic 新 schema（完整盲审）**：`dimension_analysis`（独立完整论证）、`coverage_audit`（逐条拿需求原文核对
  covered 与否）、`contradictions`（每条含原文引用）、`over_confidence_audit`、`counter_arguments`（对 Generator
  方向的反方完整论证）。
- **Reviewer 新 schema（完整评审人工分）**：`verdicts`（每维 `{verdict, adjusted_score, full_analysis,
  counter_to_human}`）、`bias_analysis`（完整含 evidence）、`need_reconfirm`（完整清单）。
- 每个 Agent 的原始完整输出被调用方拿到（不只解析后的分数），并写入档案（见 1.2）。
- 兼容性：同时保留轻量兼容字段（`dimension_scores` / `reasons` / `verdicts` / `bias` 等），由归一化函数从新
  schema 推导，置信度、分歧计算与旧接口/测试不受破坏。

### 1.2 完整过程留痕（`diagnosis/orchestrator.py` + `diagnosis/archive.py`）

- 档案新增 `generator_full` / `critic_full` / `reviewer_full`：每次 Agent 完整输出原文+解析，每版本保留
  （`_build_report` 把三者写进每一版 report，`versions[]` 累积）。
- 新增 `agent_log[]`：记录每一步（start / review / next_version）的角色、时间、完整输出，中间产物不丢。
- `get_run_state` 返回 `generator_full` / `critic_full` / `reviewer_full` / `agent_log` / `deliverable`，
  继续历史诊断时仍能看到完整对抗过程。
- start / review / next_version 各步都把 Agent 完整输出写入档案并追加 agent_log。

### 1.3 报告 = 多章节需求文档（`cases/render.py` 的 `build_diagnosis_html`）

重写为长文档，章节（实测 14 章正文 + 文档信息 + 目录，可打印数十页）：

1. 封面与文档信息（客户/版本/日期/验收人/修订历史）
2. 执行摘要
3. 需求理解与背景
4. 项目目标与范围（做什么/不做什么）
5. 功能需求（Generator 草稿 + 各轮反馈累积）
6. 非功能需求（性能/安全/合规/可用性）
7. 五维可行性深度分析（每维完整论证 + evidence 原文引用 + 对客户影响）
8. 数据与资源要求
9. 风险与缓解（完整清单）
10. 假设与依赖
11. 开放问题与待澄清（多轮累积）
12. 分阶段实施建议
13. 验收标准
14. 附录 A：完整对抗评审过程（Generator/Critic/Reviewer 全文，不删减）
15. 附录 B：多轮客户反馈与版本演进

- 每维可行性分析含「完整论证 + 引用需求原文的 evidence + 对客户影响」，不是一两句。
- 深度策略：结构化多章节 + 每轮反馈累积增长（v2 比 v1 更厚，见自测）。

### 1.4 定稿后的保存与打开（`core/api.py` + `web/app.js`）

- 定稿接口 `/diagnosis/finalize` 在人工确认后**自动生成交付物**（HTML + 尽力 PDF），响应带醒目
  `deliverable`：`html_url` / `pdf_url` / `path`（`tmp/web/cases/<id>/deliverable.html`）。
- 前端定稿结果顶部展示醒目的「打开报告（HTML/PDF）」按钮 + 保存路径。
- 交付物信息写入档案（`archive.deliverable`），历史诊断恢复（`get_run_state`）时仍显示「打开报告」按钮。
- 诊断页完整对抗评审过程全文展示（`fullGeneratorHtml` / `fullCriticHtml` / `fullReviewerHtml`），不只显示总结。

### 1.5 多轮累积（`diagnosis/orchestrator.py` 的 `next_version`）

- 客户反馈条目通过 `feedback.categorize_feedback_items` 归类为「功能需求 / 非功能需求 / 开放问题 / 验收标准」，
  织入 `generator.feedback_weave`；报告 `_build_report` 把 `feedback_weave` 写进各对应章节。
- 报告随版本累积变厚：`version_history[]` 记录每版变更；附录 B 记录每轮反馈（来源/倾向/触达维度/条目）。
- `next_version` 的 merge 对齐 `dimension_analysis[].score` 与合并后的 `dimension_scores`，保证增量模式下
  报告内分数一致。

## 3. 运行 / 验证方式

```bash
source venv/bin/activate
python -m pytest tests/          # 回归：现有 97 个用例全绿

python -m core.main              # 启动服务器，端口 8100
# 浏览器打开 http://localhost:8100  → ① 需求诊断
```

跑真实诊断（AI助教场景）：
1. 输入需求（如高校在线教育平台「AI 助教」）→ 开始诊断 → 前端展示 Generator/Critic 完整对抗过程。
2. 人工打分 + Reviewer 评审 → 确认定稿 → 前端出现「打开报告（HTML/PDF）」按钮 + 保存路径。
3. 客户反馈 → 生成下一版 → 再定稿 → 报告随版本累积变厚，附录 B 记录每轮反馈。

## 4. 自测结果

- `pytest tests/`：**97 passed**。
- 真实 DeepSeek 跑通 `start → review → finalize → 生成报告`：AI助教场景 v1 报告 HTML ~72KB、16 个 h2 章节、
  正文文本约 6.5 万字符；PDF 由 Chrome headless 成功生成。
- 多轮累积：v1（72,170B HTML / 64,478 字符文本）→ 客户反馈 3 条 → 增量重评（data 3→2）→ v2（87,138B HTML /
  79,545 字符文本），**v2 明显变厚**；附录 B 含 1 轮反馈 + 版本历史 v1/v2。
- 定稿后自动生成交付物：`tmp/web/cases/<id>/deliverable.html`（+ `.pdf`），打开链接与保存路径均可用。
- 历史诊断继续：`GET /diagnosis/{run_id}/state` 返回 `generator_full`/`critic_full`/`reviewer_full`/`agent_log`/
  `deliverable`，刷新不丢。
- 前端零构建：纯 HTML/JS/CSS，无 node 依赖；`node --check web/app.js` 语法通过。
