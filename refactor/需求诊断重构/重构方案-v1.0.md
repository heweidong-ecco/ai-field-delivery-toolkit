# 需求诊断重构方案 v1.0

> 经 grilling 多轮决策压测后收敛的权威方案。日期:2026-08-29。配套:[决策过程-v1.md](./决策过程-v1.md)、[v0 基线](./历史版本/v0-当前实现基线.md)。

## 1. 背景与动机

- 当前实现 = 单次 LLM 打分 + 简单五维评分 + 规则兜底。用户判断:**没有价值,不如直接用 DeepSeek 网页对话**。
- 人在写需求时,头脑中的信息量是文本的 10 倍,一次对话写不全。
- 需求真实链路是循环的:`生成需求报告 → 客户评估 → 上传客户反馈 → 再生成 → 再确认`,是一个 **Agent loop**。
- 结论:**单次打分无价值,价值来自"多轮渐进剖析 + 版本化交付 + 客户反馈闭环 + 全链路留痕"**。

## 2. 价值定位

- 输出给客户的**正式文档**(Q1=C)。
- 不可替代价值:**可审计的迭代交付**——每版报告、每轮 AI 剖析、每个人机分歧都结构化落盘,形成可追溯的需求演化档案;网页对话做不到版本与留痕(Q7)。
- 打分是**过程参考,不装权威**(Q2):无真实项目可校准阈值,按时效 + 最优解设计,不做精确校准。

## 3. 目标架构

### 3.1 三个 Agent 角色(分工严格、边界完整,非简单 prompt;Q13)

| 角色 | 职责 | 评审方式 |
| ---- | ---- | ---- |
| **Generator** | 剖析提问、五维打分、起草报告 | — |
| **Critic** | 独立评审 Generator:需求支持度(硬标准)/ 一致性 / 过度自信 / 遗漏 | **盲审**:不看 Generator 结论,独立打分后对比 |
| **Reviewer** | 评审**人工打分**:逐维「同意 / 修正+理由」+ 整体偏置检测(如人工系统性偏高) | **盲审**:不看 AI 原始分,避免锚定 |

> 用户强调:**必须对抗式评审**。生成、检查、评审分开,防止"自己给自己打高分、认为自己完全正确的幻觉"(Q15)。LLM 是生成式推理,单 Agent 置信度极低,不能自评自信。

### 3.2 三层循环(共用同一份需求档案;Q8)

- **剖析循环**(内部):AI 基于需求逐轮提问补全信息,默认 2-3 轮(一期先做 1 轮可选)。
- **复核循环**(核心新增):AI 打分 → 人工调分 → **AI(Reviewer)再评分人工** → 收敛或人工喊停。收敛条件 = 各维分歧 ≤1 或人工声明"以此为准";不收敛则**保留分歧进报告**。
- **版本循环**(外部):v1 报告 → 客户反馈文件 → 提炼客户意见条目 → **增量重评** → v2,带"相对上一版变更清单"。(二期)

### 3.3 定稿管线

`Generator 草稿 → Critic 意见 → Reviewer 意见(评人工)→ 人工强制确认关卡 → 合并成分版本报告`

- **人工强制确认(Q20)**:不点"我已确认"不出正式报告——"发客户"这道门只能人开。
- **分歧即信息(Q3)**:AI 与人工、Generator 与 Critic 的分歧全部保留进报告,作为过程证据,不压平。

### 3.4 置信度(Q18)

- **置信度 = Generator 与 Critic 的一致度**(可计算,不靠 LLM 自评)。
- 阈值:一致度 ≥0.8 = 高;0.6–0.8 = 中;<0.6 = 低。
- **低置信度维度强制进"需人工/客户确认"清单**——置信度要足够高且有力度,不是装饰。

### 3.5 预算(Q16)

- 单次诊断调用数封顶 ≈ **9 次**(剖析≤3×1 + Generator + Critic + Reviewer + 报告)。
- 超预算 → 提示"人工接管"。

### 3.6 存储(Q10 / Q22)

- JSON 按 `run_id` 组织:`tmp/web/diagnosis/<run_id>/`。
- 档案字段:`requirement`(原文)、`prompt`(+`prompt_modified`)、`rounds[]`(剖析问答)、`scores{generator, critic, reviewer, human}`、`divergences[]`、`confidence`、`versions[]`(每版内容 + 变更清单 + 客户意见条目)、`client_feedback[]`。

### 3.7 技术底座(Q12 / Q17)

- **`core/llm.py` 统一 DeepSeek 客户端**(结构化输出 + 失败降级 + 计费打点),**按需懒加载**;诊断 / 原型 / 飞轮复用,不各自 `from openai import OpenAI`。
- `diagnosis/` 内写**轻量确定性管线式多 Agent 编排器**;**不碰 `prototype_assembler` 的 ReAct harness**(自主循环对固定管线是负担)。
- 提示词:可自定义,但**保留强制中立条款**,报告标注「提示词已修改」且不再承诺中立(Q5=C)。
- 兜底:模型不可用 → 输出**方向信号**(偏高/中/低)并明确标注非 AI,**不给会被人当真的精确分**(Q6)。

## 4. 一期方案(待实现)

**范围**:把"生成/检查/评审分开"和"AI 再评分人工"跑通,交付单版定稿报告。

- [ ] `core/llm.py`:统一客户端(chat + 结构化 JSON 输出 + 失败异常 + 可选计费打点)
- [ ] `diagnosis/agents.py`(或拆分):Generator / Critic / Reviewer 三个独立角色的 system prompt(边界严格完整)与调用封装
- [ ] `diagnosis/orchestrator.py`:管线式编排(剖析 1 轮可选 → Generator → Critic 盲审 → 人工打分 → Reviewer 盲审人工 → 定稿),预算计数器
- [ ] `diagnosis/archive.py`:按 `run_id` 落盘 JSON 档案(字段见 3.6),每次调用追加
- [ ] `core/api.py` 升级 `/diagnosis/ai`(多 Agent)与 `/diagnosis/report`(定稿含分歧/置信度/人工确认标记)
- [ ] 前端诊断页改向导:需求 → 剖析(可跳过)→ 打分 + 对抗评审 → 人工复核 + AI 再评 → 定稿(强制确认)
- [ ] 测试:3 个角色注入式(LLM 打桩)+ 置信度计算 + 预算封顶 + 档案落盘

**一期验收**:单次诊断产出 = 多 Agent 对抗评审 + 人工复核 + 置信度 + 分歧清单 + 强制确认的定稿报告;现场可用、不依赖真实校准。

## 5. 二期方案(待实现)

- [ ] 版本循环:v1 报告 → 上传客户反馈文件(文本/PDF,预留图片)→ LLM 提炼"客户意见条目" → 触发 v2
- [ ] **增量重评**:只对客户意见触及的维度重跑 Generator+Critic,其余沿用;报告带"相对上一版变更清单"
- [ ] 整轮重跑:留给"人工判定需求本质变了"的显式操作
- [ ] 档案检索:跨 `run_id` 查询需求/版本/历史
- [ ] 置信度在版本间的演化展示

**二期验收**:完整闭环 `v1 → 客户反馈 → v2 → 确认`,客户能逐版看到变更;档案可回溯重放。

## 6. 验收标准(整体)

- 一期交付即可用(按时效 + 最优解,不追求不可得的校准)
- 每版报告带变更清单;置信度有力度的生效(低置信强制确认)
- 全部过程(问答/打分/分歧/反馈)留痕,可追溯
