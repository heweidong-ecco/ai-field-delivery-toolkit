## 1. 本轮变更

### 核心：项目作战台聚合（非壳）

新增 `projects/warroom.py::build_warroom(project_id)`，真实跨模块拉取并过滤：

1. **project**：`projects.archive.get_project` 原样返回。
2. **workflow**：项目级过滤后的状态（见下方「workflow 按项目过滤（真修）」）。
3. **diagnosis_runs**：从 `diagnosis.orchestrator.list_runs()` 全量扫描，匹配取并集——
   run 档案 `project_id == pid` **或** 项目事件里 type=diagnosis 的 `ref == run_id` **或** 该 run 客户 == 项目客户。
4. **dataprep_runs**：`dataprep.service.list_tasks` 过滤 `project_id == pid`。
5. **mapping_runs**：`mapping.service.list_mapping_runs` 过滤 `project_id == pid`。
6. **cases**：`cases.archive.list_cases` 过滤 `project_id == pid` 或客户匹配。
7. **assets**：`assets.archive.list_assets` 过滤 `project_id == pid` 或 `customer == 项目客户`。
8. **indexed_kbs**：`retrieval.service.list_indexed()` 中 `kb_run_id` 属于本项目数据作战流 run 的。
9. **events**：完整时间线。
10. **counts**：各分区数量 + `workflow_progress` 百分比。

每类给**摘要字段**（名字/状态/进度/成功率/URL 可跳转），控制条数（每区 20 条），不返回巨量数据。
返回结构 `{project, workflow, counts:{...}, diagnosis_runs, dataprep_runs, mapping_runs, cases, assets, indexed_kbs, events}`。

新端点 `GET /api/v1/projects/{pid}/warroom`（旧 `GET /projects/{pid}` 不动）。

### 补丁：诊断 project_id 落盘（聚合可靠的基础）

- `core/api.py::diagnosis_finalize`：算出所属项目 `pid` 后**写入诊断 run 档案**（`diagnosis.archive.update_run`，只增 `project_id` 字段，旧档案兼容），并把 pid 传给 `cases/service.py::create_diagnosis_case`。
- `cases/service.py::create_diagnosis_case(run_id, project_id=None)`：显式传入优先，否则回退读 run 档案的 `project_id`；case meta 落 `project_id`（只增）。
- `GET /api/v1/diagnosis/runs` 列表项带 `project_id`（只增字段）。

### workflow 按项目过滤（真修，不是壳）

重做 `core/workflow.py::project_status(project_id)`：

- **当传入 project_id 时，每步 done 必须按本项目判定**：
  - diagnosis：项目有 `diagnosis` 事件 **或** 诊断 run 档案 `project_id == pid`
  - data_prep：dataprep run `project_id == pid` **或** 项目有 `dataprep` 事件
  - prototype：项目事件 type∈prototype/iteration
  - deploy：项目有 mapping run `project_id == pid` **或** `deploy` 事件
  - deliver：项目有 case `project_id == pid` **或** 文档包 case
- **project_id 为空时保持原全局行为（兼容）**。

明确：现有 `/workflow/{project_id}` 行为从「全局判定」修正为「按项目判定」是**有意修复**，不是破坏——原实现多处看全局档案不按项目过滤（诊断/标注/映射/文档包证据来自全局），某项目状态会被其它项目产物撑高。此修复写入本更新日志与 CHANGELOG。

### 前端（⑧ 升级为「项目作战台」，零构建）

`web/app.js::loadProjectDetail(pid)` 重写为作战台渲染（改请求 `GET /projects/{pid}/warroom`）：

- 头部：项目名 + customer + 创建时间
- 概览统计卡：诊断 N / 数据任务 N / 映射 N / 交付物 N / 资产 N / RAG N / 工作流进度百分比
- 工作流进度（带门禁，项目级）
- 各产物分区：诊断列表（点击跳 ① 续做）、数据作战流任务（跳 ③ 续做）、映射（跳 ⑨ 续做）、交付物（HTML/PDF 链接）、资产（一键接入）、RAG 索引状态；每区有「去 ③/⑨/① 操作」跳转
- 保留：手动事件表单、文档包按钮、时间线

**带上下文跳转**：`gotoTab(tabKey, ctx)`（ctx 可含 project_id/customer/run_id）——跳 ③/⑨ 时预填 create 表单的项目/客户，跳 ①/③/⑨ 续做指定 run。`gotoProject` 保持兼容。

⑧ 保持能从列表进入；战场的产物区真实渲染数据（空则显示占位提示，不造假）。

### 测试（新 `tests/test_projects.py`，非教学场景）

制造业设备字段映射 / 某汽车制造厂 场景，5 用例：

1. **warroom 聚合真实**：建项目 → 诊断 finalize(打桩) → 数据任务 → 映射 run → 手写 RAG 档案（不触发 ChromaDB）→ warroom 各分区数量正确、URL 可跳、交付物 HTML 可下载。
2. **workflow 按项目过滤**：两项目，一个有产物一个没有，各自状态互不污染（诊断/deliver done 隔离，空项目全 False，证据含「诊断 run×1」项目级证据）。
3. **诊断 finalize 落盘 project_id**：run 档案 + `/diagnosis/runs` 列表项 + 交付物 case meta 都带 project_id。
4. **warroom 端点结构 + 旧端点不破坏**：新端点 10 个键齐全；旧 `/projects/{pid}` 原样；未知项目 404；`/workflow/skeleton` + `/workflow/{pid}` 正常。
5. **project_id 为空保持全局判定**（兼容）。

LLM 全部打桩；语义去重用固定哈希向量替代 chromadb 嵌入（与 test_dataprep 同法）；RAG 档案手写 archive.json（不触发 ChromaDB 下载）；资产注册表由 conftest 自动隔离。
